- Fixed: a `.bv` file whose only float BLAS use was `a @ b` on numpy arrays kept Brevi's own numpy on ARM64 (and other CPUs whose OpenBLAS kernels Brevi does not model), then stopped with a NotImplementedError at the product after printing its first lines. The build now sees the `@` and runs the program with CPython's numpy, as `.py` files already did.
- Fixed: `OPENBLAS_NUM_THREADS`, `OMP_NUM_THREADS`, `GOTO_NUM_THREADS` and numpy's OpenBLAS's other `OPENBLAS_*` settings change the order large dot, matrix-vector and matrix products add in, but Brevi's numpy ignored them and printed the default's last digits. With one set, float BLAS now runs with CPython's numpy, and the result cache keys on them.
- Fixed: Brevi's numpy counted CPUs with Rust's rule, which honours a cgroup CPU quota (`docker --cpus`), where numpy's OpenBLAS counts the CPUs the process may run on (on macOS, physical cores). Large products split across threads could then print other last digits than numpy's in such containers. It now counts as OpenBLAS does.
- Fixed: `np.linalg.solve` and `inv` from 100 x 100, and `det` and `slogdet` from 20000 values, printed numpy's one-thread digits on machines with more than one CPU, where numpy splits the LU across threads and adds in another order. Brevi now stops there with a NotImplementedError (one CPU still gets numpy's digits); `BREVI_NUMPY=0` uses CPython's numpy.
