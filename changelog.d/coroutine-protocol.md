- Coroutines in dynamic builds follow CPython's object protocol, measured with CPython's `test_coroutines` (62 wrong answers there before, 0 now; 63 of 89 tests match): `types.CoroutineType`, `GeneratorType`, `AsyncGeneratorType` and `FunctionType` are the program's own classes, so `type(c) is types.CoroutineType` holds; coroutines have `__class__`, `cr_suspended`, a dotted `__qualname__` and `__await__()` (the `coroutine_wrapper` iterator); sending to or throwing into a finished coroutine is `RuntimeError`, re-entering a running one is `ValueError`, a `StopIteration` raised inside one becomes `RuntimeError` (PEP 479), and a coroutine that was never awaited issues CPython's `RuntimeWarning`. `async with` and `async for` raise CPython's errors for a bad context manager or `__anext__` result, and `copy.copy` of a coroutine is `TypeError`.
- An exception the runtime raises inside an `except` block (`1/0`, `[][1]`) now has the handled exception as its `__context__`, as in CPython.
- Refused when the program is built (dynamic builds): a coroutine's or async generator's `cr_frame`, `cr_code`, `cr_await`, `cr_origin`, `ag_frame`, `ag_code`, `ag_await`, and `types.coroutine` in any use but one.
- `@types.coroutine` as the innermost decorator of a generator function works natively, as in CPython: the function comes back itself with `CO_ITERABLE_COROUTINE` set, its generators can be awaited and can `yield from` a coroutine, and they are not `Awaitable` or `Coroutine` instances. Awaiting a coroutine that is suspended part-way raises CPython's `RuntimeError` ("coroutine is being awaited already").
