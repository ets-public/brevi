- **The typed build no longer gives wrong answers when two names share a list.** The 10 November review found seven ways the typed build copied a list, dict or set where Python shares it: `xs.sort()` in a function, the same row appended in a loop, a stored list changed later, inner lists shared (`[row] * 3`), a global set again to another type after a function uses it, a field list sorted in a method, and a list cleared while a loop walks it; deleting from a list in a loop also stopped the program. The alias check matched patterns; it now has a proof behind it over the whole program (`src/share_guard.rs`) that follows which names, fields, function results and containers can hold the same list, through calls, returns, loops and lambdas. A program is built typed only when no shared list is changed while another name for it is still used, or when the typed build provably shares it too: the parameter is passed by `&mut`, the loop walks the list in place, or the object is a class instance or row, which rustc checks. Anything else is built on the dynamic build, which follows Python's rules. A function that sorts, reverses, extends or adds to a list it is given now changes the caller's list in the typed build as well, so `tests/verify/shared_sort.py` is typed and identical. A loop that rebinds its loop variable (`line = line.strip()`) no longer writes into the list.
- **The fuzzer shares lists.** `tools/fuzz.py` makes aliasing cases (one case in four; `--alias-only` for only those), and the review's repros and the fuzzer's finds are in `bench/fuzz/corpus/share_*.py`, which every pull request replays against CPython on both builds.
