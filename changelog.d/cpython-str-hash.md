- Dynamic builds hash `str` and `bytes` exactly as CPython 3.13 does (SipHash-1-3 over the PEP 393 form), keyed from `PYTHONHASHSEED` as CPython reads it (unset, empty or `random`: a random key; `0`: the all-zero key; an invalid value stops at startup with CPython's fatal error). At a fixed seed, `hash()` of a string and the order of a set of strings match `python3`. Under `--sandbox` the key is CPython's for `PYTHONHASHSEED=0`.
- The typed build no longer walks a set of strings in its own order: such programs take the dynamic build, whose order is CPython's.
- Conformance runs CPython and both builds at `PYTHONHASHSEED=0`, so tests whose output depends on string hashes are scored.
- Dynamic builds lay out a set literal of constants as CPython 3.13 does: the frozenset constant is rebuilt once more when one of its strings is already interned (a name in the module, or one of the strings CPython interns at startup, `tools/gen_interned.py`), and `for`, comprehensions and `in` use that frozenset itself. Bytes and imaginary literals are constants too; a set of folded constant expressions (`{1+1, 2, 3}`) is refused at build time, and a module imported at run time stops with "not supported" when its literal's order depends on strings interned before it (fixed `PYTHONHASHSEED` only).
- Dynamic builds: `d.fromkeys(...)` on an instance of a dict subclass builds that subclass. A program that uses `re` and calls `hash()` is refused at build time (CPython hashes a compiled pattern over its sre code), and hashing a `re.Pattern` otherwise stops with "not supported".
