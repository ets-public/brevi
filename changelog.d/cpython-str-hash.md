- Dynamic builds hash `str` and `bytes` exactly as CPython 3.13 does (SipHash-1-3 over the PEP 393 form), keyed from `PYTHONHASHSEED` as CPython reads it (unset, empty or `random`: a random key; `0`: the all-zero key; an invalid value stops at startup with CPython's fatal error). At a fixed seed, `hash()` of a string and the order of a set of strings match `python3`. Under `--sandbox` the key is CPython's for `PYTHONHASHSEED=0`.
- The typed build no longer walks a set of strings in its own order: such programs take the dynamic build, whose order is CPython's.
- Conformance runs CPython and both builds at `PYTHONHASHSEED=0`, so tests whose output depends on string hashes are scored.
- Dynamic builds lay out a set literal of constants as CPython 3.13 does: the frozenset constant is rebuilt once more when one of its strings is already interned (a name in the module, or one of the strings CPython interns at startup, `tools/gen_interned.py`), and `for`, comprehensions and `in` use that frozenset itself. Bytes and complex literals (`2j`, `1+2j`) are constants too; a set of folded constant expressions (`{1+1, 2, 3}`) is refused at build time, and so is a set literal of 2 or more constants in an imported module whose order the program walks when that order depends on the strings CPython interned before importing it (some seed always reorders it); in a library module Brevi copies (jinja2), the program stops with "not supported" instead, only at a fixed `PYTHONHASHSEED` where the two possible orders differ.
- Dynamic builds: `d.fromkeys(...)` on an instance of a dict subclass builds that subclass. `hash()` of a compiled `re` pattern is refused at build time when the build can see it (CPython hashes the pattern over its sre code), and stops with "not supported" otherwise.
