# Brevi benchmark

Small and big stdin/stdout tasks (`tasks/`), each with tests generated by the reference solutions in `ref/gen.py`.
A model solves each task in one language and checks it with `run.sh LANG TASK FILE`, which logs every attempt to `logs/`.
`python3 analyze.py "logs/round1/*.jsonl"` prints the summary.

Token counts are exact: `tokcount.py` asks Anthropic's count_tokens endpoint (Sonnet tokenizer, `claude-sonnet-5-5`) and caches results by content hash in `tokcache.json`. It needs `BENCH_ANTHROPIC_KEY`. Logs marked `"tok":"exact"` use it; older logs (runs before `e1`) hold estimates from `esttok.py` (words, numbers and symbols), which undercount by 12 to 19%.
Each check also logs `patch_tok`: for a retry, the tokens of the lines changed since the last check (removed plus added, never more than the file), from `patchtok.py`. `analyze.py` prints both `loop_total` (every check counts the whole file) and `patch_total` (retries count as patches). `retro_patch.py RUN...` scores older runs the patch way from their saved attempts.
`python3 recount.py` counts every saved solution and error output both ways and writes `logs/recount.json`.
`run.sh` uses `../target/release/brevi` unless `BREVI` is set (runs before the rename are named `-axon`).
`python3 subject_prompt.py RUN LANG small|big` prints the prompt given to a test-subject model; subjects may only run code through `run.sh`.

## Release test (plain Python, since 1 Nov 2026)

Brevi's release test is the plain-Python trial: the model gets the ordinary Python prompt and tools, writes `.py` files, and Brevi builds and runs them in place of CPython. Plain Python runs the same day as the baseline:

```
python3 e2e.py RUNa --lang pyb --model sonnet --set rel --jobs 4
python3 e2e.py RUNa --lang python --model sonnet --set rel --jobs 4
# the same with --model haiku, then runs RUNb, RUNc, RUNd
# DeepSeek: the same with --model deepseek (deepseek-flash, V4.1 Flash) or deepseek-pro (deepseek-v4-pro); needs DEEPSEEK_API_KEY
python3 e2e.py --summary "logs/e2e/RUN*.jsonl"
python3 e2e.py --verdict "logs/e2e/RUN[a-d]-*.jsonl"   # checks the bar below and prints a 95% range for each cost ratio
```

### Release suite (set `rel`, since 3 Nov 2026)

Up to e34 the release test used the six xl3 tasks, so one task that took an extra check moved a run's cost ratio by several percent. On the four runs that passed the bar (e31 to e34) Sonnet's ratio was 1.098x, but resampling the tasks puts its 95% range at 1.02x to 1.20x: the pass was not decisive. The set `rel` adds 18 held-out tasks from `ref/gen_rel.py` to the six xl3 tasks, 24 in all. They were written for this test and have not been used to tune Brevi:

| Size | Tasks | What they exercise |
| --- | --- | --- |

In e18 only 3 of 24 first attempts were rejected while CPython ran them, and every first attempt that built printed what CPython prints. `py_as_brevi.py` tracks the share of saved Python solutions that Brevi builds and runs correctly unchanged.

## Where pyb loses tokens (3 Nov 2026)

In the release test both sides get the same prompt, so pyb can only lose tokens when Brevi itself makes a check fail. Since run `sh1a`, every pyb check also runs the same files with CPython and logs the pair (`shadow`: `[pyb passed, CPython passed]`); the summary's `bug` column counts checks that failed only because of Brevi. In four Haiku runs on xl3 (`sh1a` to `sh1d`, main 9408924), 0 of 9 failed first checks were Brevi's: CPython failed the same code. The other numbers from those runs: about 65% of output tokens are hidden thinking and 30% code, and retries add little output, so Brevi cannot save much on these tasks by changing what a failed check prints. `replay.py` measured that: replaying the 9 failed checks 3 times each with a shorter feedback (only the differing output lines) cost 14% less after the branch point than the current feedback, which is about 2% of a whole run.

A replay found one real bug: `out.extend(errs)` on a list parameter was lost in typed builds, and the model spent 7 checks on it and failed the task.

### Time-limited set (`speed`)

Four tasks from `ref/gen_speed.py` with small inputs and heavy work (`conway`: Game of Life up to 600x600 for 500 generations, 0/1 knapsack up to 1000 items and capacity 300,000, edit distance up to 10,000 letters, Collatz chains up to 3,000,000), under the usual 10 s test limit. The plain solutions take CPython 15 to 80 s. The question was whether Brevi's speed saves the retries an agent spends making CPython code fast enough. Run `s1a` (one run each, main 9408924 plus the first fixes) said no: the models wrote fast Python from the start (big-int bitboards, bit-parallel edit distance, bit-packed knapsack), and Brevi built those programs badly.

| s1a | Python passes | Python $ | pyb passes | pyb $ | pyb checks failed only because of Brevi |
| --- | --- | --- | --- | --- | --- |
| Sonnet | 4/4, all first try | $0.087 | 4/4, 1 first try | $0.306 | 4 |
| Haiku | 4/4, 3 first try | $0.012 | 3/4, 1 first try | $0.019 | 2 |

The causes, all fixed since: big-int `&`, `|`, `^` raised NotImplementedError in dynamic builds; `bin()` and `int(s, 2)` of big ints were quadratic; `2 ** n` squared huge numbers; `>>` by more than about a million bits shifted by a million; bit-packed ints in typed builds overflowed 64 bits; a grid row changed cell by cell was copied back after every cell (Game of Life 16 s typed, now 2.6 s against CPython's 30 s); `min(a, b, c)` and `map(sum, rows)` sent programs to the slower dynamic build.

Run `s1b` (one run each, after those fixes, PR #139): Sonnet pyb $0.109 against Python $0.127 (0.86x), 4/4 both, 3 first try both, no check failed because of Brevi. Haiku pyb $0.018 against $0.011, 4/4 both; its whole gap is one knapsack solution that packs 300,000 fields into one int, which the dynamic build ran in 10.5 s against CPython's 6.2 s (two timeouts the model then worked around). Big-int operations now borrow their operands instead of copying megabytes of limbs, which brings that program to 7.1 s.

Release suite `rel` with the shadow check, runs `u1a` and `u1b` (3 Nov, branch after PR #139): Sonnet 1.095x Python (per run 1.00x to 1.22x), Haiku 1.114x (0.98x to 1.28x), native builds 47/48 and 45/48, so the 10% bar was missed. 19 checks failed only because of Brevi, from seven bugs, all fixed since: None from a function that also returns a list read as an empty list (bowling, and a router task in another run), a tuple held as a dynamic value failed `isinstance(r, tuple)` (bowling), `all(c in digits for c in s)` over a dynamic text walked nothing (tellers), a list slot set by a nested function was set on a copy (sudoku), the typed build's Fraction could not hold the unit table's denominators (units, 3 runs), and the dynamic build lacked `Decimal.scaleb` (text_table, 2 runs) and `datetime.time` (cron_next). Two stray test files from the speed set had also made rel's `life` task fail in both languages.

Runs `u2a` and `u2b` after those fixes (PR #140, both languages and models): the bar is met. Sonnet pyb costs 0.970x Python (95% range 0.93x to 1.01x) and Haiku 1.007x (0.96x to 1.05x). Every task passed on both sides, and native builds were 44/48 and 46/48. No check failed because of Brevi (`bug` 0 in all four pyb runs). The remaining CPython fallbacks are csv_join and json_query.

From PR #141 the pyb prompt has one more line than the Python prompt, the line Brevi's skill, MCP server and llms.txt now give agents: "Your program is compiled to native code, which runs plain loops over ints and lists 10 to 50 times faster than CPython. Write the plain, direct solution; do not hand-optimise it for speed." (`--no-hint` drops it; the line now quotes the measured range, 1.7x to 39.5x, median 8.5x.) The outside review of 9 Nov 2026 pointed out that only the pyb side got the line, so the saving below may come from the prompt rather than from Brevi. `--lang pyh` is the control for that: the Python prompt with the same line, checked with CPython. A fair heavy-task comparison is `pyb` against `pyh`, not against `python`.

- **Speed set with the control** (runs `sp3a`, `sp3b`, 9 Nov 2026, main at #282, two runs per model): Sonnet pyb $0.0729 per run against pyh $0.1594 (0.46x); Haiku pyb $0.0052 against pyh $0.0154 (0.34x). Every pyb program passed and built natively (15 of 16 on the typed build), 15 of 16 on the first check. With the same line, CPython's side wrote the plain solution too, ran over the 10 s limit, and spent 10 to 12 checks per run making it fast; Haiku failed knapsack once. So the saving below survives the control, and it is the speed, not the line.

With the line, on that branch (3 Nov 2026, CPython told nothing):

- **Speed set** (runs `sp2a`, `sp2b`): every task passed on both sides, all pyb programs built natively, and no check failed because of Brevi. Sonnet pyb cost $0.128 against Python's $0.222 (0.58x). Haiku pyb cost $0.0117 against $0.0221 (0.53x). Python, told nothing, still hand-optimises, and that costs it twice the output.
- **Release suite** (runs `v1a`, `v1b`): the bar is met. Every task passed. Sonnet came in at 1.074x (95% range 1.03x to 1.12x) and Haiku at 0.997x (0.95x to 1.04x). Native builds were 45/48 and 47/48, and no check failed because of Brevi. Sonnet's pyb runs cost $0.74 against $0.68 in `u2a`/`u2b` without the line. The research thread's single run with the line had $0.722 against $0.727. So the line shows no clear effect on ordinary tasks, and four runs (`u2` + `v1`) average about 1.02x for Sonnet.

## End-to-end benchmark (`e2e.py`, 1 Nov 2026)

`run.sh` scores code written plus errors read. `e2e.py` counts everything the Claude API bills for a finished task: the system prompt (the Brevi guide, cached), tool calls and results, thinking, text and retries, read from each response's `usage`, and prices it in dollars. Each task is a fresh conversation with the same tools in both languages (`write_file`, `edit_file`, `check`, plus `guide` for Brevi). `python3 e2e.py RUN --lang brevi --model sonnet --set xl3` runs a set; `python3 e2e.py --summary "logs/e2e/*.jsonl"` prints totals. Task sets live in `subject_prompt_sets.py`.

Held-out XL set 3, effort medium, two runs (e1, e2), 12 tasks per row, every task passed:

| Model | Language | Passed at first check | Output tokens | Guide cache write | USD |
| --- | --- | --- | --- | --- | --- |
| Sonnet | Brevi | 9 | 39,228 | 57,085 | 0.564 |
| Sonnet | Python | 11 | 26,905 | 32,674 | 0.358 |
| Haiku | Brevi | 5 | 129,526 | 134,824 | 0.085 |
| Haiku | Python | 7 | 72,542 | 80,475 | 0.047 |

Brevi costs 58% more than Python with Sonnet and 78% more with Haiku. Most of the gap is output (thinking and text, 46% more with Sonnet, 79% with Haiku) and the guide in the prompt; the finished code is about the same size. This is a larger gap than the code-and-errors benchmark shows.

Third and fourth runs (e3 cold, e4w one task at a time so the guide stays cached) keep each conversation in `work/e2e/.../conversation.json`, with thinking summaries. With a warm cache the guide costs almost nothing (about 4,600 cached tokens read per call). The gap is model output and the cache writes of that output in later turns: Sonnet Brevi $0.315 vs Python $0.187 (e4w). The thinking summaries show why: in Brevi, models stop to work out rules that differ from Python, mostly the scope of top-level names (3 of 8 Sonnet and 5 of 10 Haiku thinking blocks), plus copies vs `mut`, `Result` and whether a parser accepts a form. Python runs show none of this. `--thinking between_tools` turns thinking off on Sonnet for comparison.

`python3 py_as_brevi.py` hands every saved Python solution to `brevi check` unchanged and lists the most common first errors. On 1 Nov 2026, 56 of 580 (9.7%) pass. The top blockers are `;` between statements (126), `import` lines (sys, json, datetime, heapq, csv), `def main()`, raw-string regexes, `|`/`&` on sets, and `.splitlines()`/`.rstrip()`. After the library batches (#32 to #39) and the roadmap thread's syntax work, 271 of 580 (46.7%) pass the fast check and 162 (27.9%) also build (`--full`).

The strictest test of "Python in, Rust speed out" is `--lang pyb`: the model gets exactly the Python prompt and tools, writes `.py` files, and `check` builds them with Brevi instead of running CPython (run `e10`, same 6 tasks). None of the 6 programs built at the first check with either model. Sonnet cost $0.421 (5 of 6 passed) against $0.189 in Python; Haiku $0.046 (2 of 6) against $0.026. The blockers were all plain Python the compiler did not accept yet: lists of mixed types, untyped module globals and `x = None`, some annotations (`tuple[int, ...]`, string annotations), docstrings in imported files, `xs[:] = ...`, `not a <= x <= b`, for/else, and library calls (`set.update`, `format(x, spec)`, `datetime.strptime`, `timedelta`, `calendar.monthrange`). The library calls are now supported; the syntax items are with the parser work. Run `e11`, after the library batches (#47, #48, #49) and the parser batch (#46): Sonnet $0.513 (4 of 6 passed, 0 built at the first check), Haiku $0.044 (4 of 6, 1 built at the first check; e10 was 2 of 6). The errors left are almost all type inference on unannotated Python: dicts used as mixed-type records, parameters and return types that cannot be worked out, module-level names used in functions, and `x = None` that later holds a dict. Run `e12`, after #50 to #52 (shared values written back, unlimited ints, more inference): Sonnet $0.396 (5 of 6 passed, 1 built at the first check), Haiku $0.037 (5 of 6, 2 at the first check). Plain Python on the same tasks costs $0.189 and $0.026, so the gap went from 2.2x to 2.1x (Sonnet) and from 1.8x to 1.4x (Haiku) since e10. Run `e13`, after #53 and #55 (class fields, module globals, mixed records, loop write-back): Sonnet $0.275 (6 of 6 passed, 4 built at the first check), Haiku $0.029 (4 of 6, 4 at the first check). That is 1.45x and 1.1x plain Python. Without the quiz task, whose records hold a different type in one tuple slot per question kind, Sonnet costs $0.157 against $0.146 in Python and Haiku $0.017 against $0.020. Run `e14`, after #56 and #57 (values whose type differs per row held as JSON, import aliases), with plain Python rerun the same day for a fair baseline: Sonnet $0.205 (6 of 6 passed) against $0.176 in Python (6 of 6), so 1.16x; Haiku $0.024 (5 of 6) against $0.025 (6 of 6), so 0.94x. Haiku's one failure (quiz) is also wrong when run with CPython. Every first attempt from e11 to e14 except that one now builds and matches Python's output.

## CPython conformance

`tools/conformance.py` measures how much of Python Brevi handles with a source outside this repository: CPython's own test suite. The latest committed result is [conformance/report.md](conformance/report.md). It runs in CI as a ratchet on every pull request that touches the compiler (`.github/workflows/toolchains.yml`, one toolchain, about 10 minutes): `--check` fails on a wrong result or crash not in `compat/conformance_known_wrong.txt`, on a line there that is no longer wrong (so the list only shrinks), and when fewer tests match than `compat/conformance_floor.json` allows (so the score only rises). `--write-baseline` resets both after a run whose results have been read. To run it by hand, for example before a release:

```
cargo build --release
python3 tools/conformance.py --check --out bench/conformance   # 5 to 10 minutes, four tests at a time
python3 tests/conformance_test.py                              # the extractor's unit tests, no network
```

- **Source.** Tests come from one CPython tag (`TAG` in the tool), fetched once into `$BREVI_CACHE/conformance` (else `~/.cache/brevi/conformance`) and checked against pinned SHA-256 sums, so later runs need no network. Nothing of CPython's is vendored. The reference output comes from the matching interpreter only (`python3.13` at the same patch version, or `--python`); the tool stops if the versions differ.
- **Scope.** Two slices, each published as its own number with its own floor and known-wrong list:
  - `core` (the default): `test_grammar`, `test_scope`, `test_int`, `test_list` and `test_dict`, with their inherited tests (the same list unittest would run).
  - `stdlib` (`--slice stdlib`): the modules agents use most, `test_itertools`, `test_collections`, `test_re`, `test_textwrap`, `test_functools` and `test_string` (`test_heapq` and `test_bisect` load their module through `import_fresh_module`, which the extractor cannot follow yet). Its result is in [conformance/stdlib/report.md](conformance/stdlib/report.md), and its lists are `compat/conformance_stdlib_known_wrong.txt` and `compat/conformance_stdlib_floor.json`. It takes about as long as `core`, so CI checks it only in the daily run.

  To add a file, add it with its hash to `SOURCES` and to its slice in `SLICES`.
- **Extraction.** Each test method becomes a script holding what it needs: helpers, `setUp`, and base classes when it uses `self`. Assertions become prints: `assertEqual(a, b)` prints `repr(a)`, and `repr(b)` too unless `b` is a plain literal, `assertTrue(x)` prints `bool(x)`, `assertRaises` prints the exception's type, `assertRaisesRegex` also its message. `python3 tools/conformance.py --show ID` prints a script and how to reproduce it.
- **Decorators and warnings.** Decorators are read the way CPython applies them. A `skipIf`/`skipUnless` condition (and `requires_docstrings`) is evaluated by the reference interpreter, from a short whitelist of names; a test it skips is `excluded` ("skipped by CPython: ..."), one it runs is cut out as usual, and a condition outside the whitelist leaves the test `not_extractable`. `support.impl_detail` tests are `excluded` like `check_impl_detail` ones, and `bigaddrspacetest` like `bigmemtest`. `pickle_deprecated` (itertools) and `warnings_helper.ignore_warnings` are kept as the script's own wrappers with the same behaviour: the first runs the test three times (recording warnings, ignoring them, turning them into errors). `assertWarns` and `assertWarnsRegex` blocks record warnings and print whether a matching one was raised, with the categories seen. `eq = self.assertEqual` aliases and helper assertions defined by the test class are rewritten like the direct calls.
- **Running.** Each script runs under CPython with two `PYTHONHASHSEED` values, then `brevi build` makes it twice: the normal path and `BREVI_DYN=1`. `brevi run` is never used, as it falls back to CPython. Scripts and programs run with a timeout, no network and writes only to their own folder (`sandbox-exec`, macOS), a memory limit (`ulimit -v` on Linux, a resident-memory watch everywhere), and imports limited to `ALLOWED_IMPORTS`.

| Category | Meaning |
| --- | --- |
| `matched` | Same stdout and exit code as CPython |
| `refused` | `brevi build` gave an error: allowed by Brevi's promise, but not covered |
| `wrong_output` | Built, exit code right, stdout differs |
| `wrong_exit` | Built, exit code differs (usually an exception CPython does not raise) |
| `crash_or_timeout` | Build or program panicked, died on a signal, or hit the time or memory limit |
| `not_extractable` | No faithful script could be made, or the script fails under CPython. Stays in the total |
| `unstable` | CPython's own output changes with the hash seed or between runs. Left out of the total, with a count |
| `by_design` | Refused because the test runs a string as code (`compile`, `exec`, `eval`), which a sandboxed native binary refuses on purpose. Named in `compat/conformance_by_design.txt` (reviewed); `--check` fails on one not listed, or a listed one no longer refused that way. Left out of the total, with its count beside every score |
| `excluded` | Tests CPython's internals (`cpython_only`, the C API, reference counts). Left out of the total, each with a reason |

**coverage** is `matched` / (all - `unstable` - `excluded` - `by_design`), not counting matches where library calls ran in CPython (`pybridge`). **wrong** is `wrong_output` + `wrong_exit`. The headline is the normal build; `BREVI_DYN=1` is reported beside it.

`compat/conformance_known_wrong.txt` lists the known wrong results, one `test-id mode issue=#N owner=LOGIN expires=YYYY-MM-DD` a line, and `--check` exits 1 on a wrong result not listed and on a line with no tracking issue, owner or expiry, or past its expiry: no known-wrong entry without someone answering for it. Remove a line when its bug is fixed. `--release-gate` is the release bar: it exits 1 when the normal build's coverage is below `release_gate.coverage` in the slice's floor file (core 90%, stdlib 80%) or any known-wrong result remains. The report also gives assertion-bearing coverage (native matches whose program printed something to compare; silent matches only show the program built and exited 0) and the typed-path share of native matches. A program that ends on a signal that could mean memory unsafety is only counted in the report; its name goes to `private_signals.json` in the cache, to be read before anything is published ([SECURITY.md](../SECURITY.md)).
