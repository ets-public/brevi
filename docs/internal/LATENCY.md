# Latency harness

**Why:** the agent's inner loop is edit → check → run, dozens of times per task. Runtime speed matters only when tests are heavy; **compile latency matters every time**. The current baseline is ~144 ms median `brevi check`, ~1.2 s cold build, 5–15 s first build after install. The targets are p50 `check --fast` ≤ 20 ms, full check ≤ 50 ms, cold build ≤ 500 ms.

**What it measures** (each in a fresh subprocess, so process startup is included — that is the point):

| Metric key | Command | What it represents |
|---|---|---|
| `check_fast` | `brevi check main.py --fast` | parse + infer + guard, no `rustc` |
| `check` | `brevi check main.py` | full check (includes `rustc --emit=metadata`) |
| `build_cold` | `brevi build main.py -o <tmp> --no-cache` | a first build, every run |
| `run_cached` | `brevi run main.py` | an unchanged program replayed from the result cache |
| `run_cold` | `brevi run main.py --no-cache` | cold build + run (optional, expensive) |

Each metric reports `n`, `min`, `p50`, `p95`, `max` in milliseconds, per fixture.

## Files

- `bench/latency.py` (below) → `bench/latency.py`
- Fixtures: generated by `--make-fixtures bench/latency-fixtures/`, which creates:
  - `typed/main.py` + `work.py` + `util.py` (~110 lines across three files, stdlib only, designed for the typed path)
  - `dynamic/main.py` (~30 lines, values change type, designed for the dynamic path)
- Output: human-readable markdown on stdout, optional `--json latency.json`, optional `--markdown latency.md`.

## Usage

```bash
# one-time
python3 bench/latency.py --make-fixtures bench/latency-fixtures/

# local run (20 samples per metric)
python3 bench/latency.py --brevi target/release/brevi --runs 20 --json latency.json

# gate: fail if a threshold is exceeded
python3 bench/latency.py --brevi target/release/brevi --runs 20 \
  --max-p50-check-fast 20 --max-p50-check 50 --max-p50-build 500 --max-p50-run 10
```

Thresholds apply to the **worst fixture** (so a dynamic-path regression fails too). Exit code is 1 if any threshold is exceeded; the message names the metric and fixture.

## CI

`.github/workflows/latency.yml` runs it weekly (before the Monday release) and on `workflow_call`. Runner noise is real:

- Use p50 over ≥20 runs, and look at the **trend** across releases, not a single week.
- On shared GitHub runners, absolute gates should be generous (e.g. 2x the target); run the hard gate on a dedicated machine if one exists.
- Pin the runner image (`ubuntu-24.04`), not `ubuntu-latest`.
- Store `latency.json` as an artifact and commit a one-line history to `bench/latency/HISTORY.md` per release.

## Interpreting failures

- `check_fast` regresses → front-end work (parser, inference, guard).
- `check` regresses but `check_fast` does not → `rustc` invocation, metadata emit, or cache miss.
- `build_cold` regresses → rustc flags, prelude/rlib packaging, codegen size.
- `run_cached` regresses → result-cache key or replay path.
- Only `dynamic` regresses → dynamic runtime size/link time.

## Definition of done

- [ ] Baselines recorded in `docs/internal/LATENCY.md` and re-recorded each release.
- [ ] Latency job in CI with artifact upload and a written threshold policy.
- [ ] A regression on any metric is treated like a test failure for release purposes.
- [ ] `brevi check --fast` is documented as the agent-loop command, and its p50 is the headline latency number.
