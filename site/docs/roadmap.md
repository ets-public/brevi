# Roadmap
<!-- description: What is next for Brevi: the public preview, package managers, brevi.run, and the compiler work in progress. -->

Brevi's direction stays the same: **AI-first**, with speed and safety as the reasons an agent should run its Python through Brevi. Token savings are added step by step and each one is measured in the release test before it counts. This page lists what is planned, not promised dates.

## Now

- **Public preview on GitHub.** The source, the releases and these docs, under Apache-2.0.
- **Sandbox on every path** (v0.24.1). The `allow` check runs before every build path, Python libraries need `allow native`, and a sandboxed program never falls back to CPython. From v0.24.6 only the caller grants capabilities under `--sandbox` (`--allow`, `--allow-py`, the MCP `allow` and `allow_py` arguments); the program's own allow lines grant nothing. From the next release, `--allow-read DIR` and `--allow-write DIR` hold file access to folders, `--allow-net HOST` the network to hosts, Brevi's numpy runs with no grant, and on Linux CPython loaded under the sandbox is held to the file grants by Landlock.
- **Resource limits** (from the next release). `--limit cpu=2,mem=512,time=10,output=64,file=10` (the MCP `limits` argument on `run`, `test` and `verify`) stops a program at the first CPU, memory, wall-clock, output or file-size limit it reaches, with one JSON line naming it; `written`, `net`, `threads`, `fds` and `files` limits come with it. A [threat model](https://github.com/ets-public/brevi/blob/main/docs/THREAT_MODEL.md) says what the sandbox and limits cover and what they do not. Next: memory limits on macOS, CPU and memory limits on Windows, holding CPython's network and processes, the check-then-open race with other processes, and an outside security review once Brevi has more users and funding.
- **Agent platform templates** (in the repository now, for the next release). Ready-made setups that run an agent's Python under Brevi's sandbox and limits on [E2B, Daytona, Modal and Cloudflare](/docs/agents#agent-platforms-e2b-daytona-modal-cloudflare), and a [weekly public benchmark](/docs/benchmarks#weekly-agent-code-benchmark) of what agent code costs Claude models with Brevi and with CPython, how many tasks they finish, and how fast the programs run. Next: run each template on its platform end to end, publish the image to a registry so templates need no build, and MCP over HTTP inside the sandboxes.
- **Library programs off the typed path** (v0.24.6). A program the typed build rejects that imports a library Brevi lacks (requests, pydantic, yaml) takes the dynamic build, and only those imports run in CPython.
- **The standard library, natively.** Standard-library calls no longer need CPython. What the typed build lacks runs in the native dynamic build (since v0.24.3), and common modules move onto the typed fast path one at a time; the [changelog](/docs/changelog) lists each one. From the next release `open()`, `os.listdir`, `os.walk`, `zoneinfo`, `tzlocal` and `importlib.metadata.version` are native too, so the official MCP time server builds unchanged ([showcases](/docs/showcases)). Next: `csv.writer` on other files, `datetime.strptime` on the typed path, then `json` indent and `dataclasses.asdict` on the typed path. The [table](/docs/compatibility#what-runs-native) shows where each function runs.
- **A faster dynamic build.** Programs that don't fit the typed build run on the dynamic build, which is native but still slower than it should be: from the next release it has attribute caches, fused loops, inline float math and faster objects, and builds a program's own packages (folders with `__init__.py` and relative imports) natively, so Karpathy's micrograd trains natively 5.5x faster than CPython. Still slow: bulk pydantic validation about 15x slower than real pydantic, and polars on large frames about 13x slower than polars' own engine.
- **More programs on the fast path.** On a corpus of 813 saved agent programs, 567 build typed in v0.25.0 (565 in v0.24.5, 550 in v0.24.4, 496 in v0.24.3), and v0.24.5 fixes the typed-build wrong answers the v0.24.4 release test found (`trains`, `poker`). Next: multi-file programs where one module sends the whole program to CPython.
- **numpy, natively.** Python files that use numpy build without CPython: Brevi's own numpy (float64, int64, float32, int32, bool and string arrays, broadcasting, ufuncs, reductions in numpy's summation order, indexing, numpy's printing) checked against real numpy. What it does not have yet goes to CPython's numpy as before. `np.random` draws numpy's own numbers for the same seed (all the common distributions), and matrix products, `linalg` (`det`, `solve`, `inv`, `norm`, `lstsq`), `polyfit`, `histogram`, `cov` and `corrcoef` match numpy to the last digit. All of numpy's common random distributions are native too. Next: float32 matrix products, `np.strings` functions and numpy's multi-threaded LU for large matrices.
- **Tokenizers, natively.** `tiktoken` builds natively from the next release, with every OpenAI encoding built into the binary, so token counting and chunking need no CPython or network. Hugging Face `tokenizers` builds natively too (BPE and WordPiece tokenizers from the Hub, built into the binary). Next: Unigram models (T5, XLM-R).
- **HTTP clients, natively.** `requests` and `httpx` (with `AsyncClient` and streaming) build natively from the next release, over native sockets and TLS, and the sandbox gets a `net` grant with a host list (`--allow-net`). The Anthropic and OpenAI SDKs build natively on top of them from the next release. Next: `files=` multipart uploads, HTTP/2, networking on Windows, and shorter builds.
- **MCP servers as single binaries.** A Python MCP server on the official `mcp` SDK (`MCPServer` or the low-level `Server`, stdio) builds into one native binary from the next release, answering as the SDK does on both protocol eras up to 2026-07-28, and starting in about 25 ms where CPython takes about 0.75 s. `brevi verify` certifies a server against a recorded client session. Next: a native `logging` so servers that log stay native, the streamable HTTP and SSE transports, sampling and elicitation, and faster server builds (1.5 to 2.5 minutes today).
- **LLM SDKs, natively.** Programs using the `anthropic` and `openai` Python SDKs (sync and async clients, messages and chat completions, streaming, tool use, embeddings, the Responses API) build natively from the next release, with the SDKs' own response objects, errors and retries, and start in about 10 ms where CPython takes 0.5 to 0.9 s to import the SDK. Structured outputs (anthropic's `parse` and `output_format`, openai's `parse` and `stream` helpers) are native too from the next release. Next: the tool runners, then message batches and files.
- **pydantic, natively.** pydantic v2 models (fields, validators, `ConfigDict`, dumps and JSON, with pydantic's own error messages) build natively from the next release. `model_json_schema` and `TypeAdapter` are native too from the next release. Next: datetime fields and serializers, generic models, and a faster core.
- **jinja2, natively.** Jinja templates, including Hugging Face chat templates, render natively from the next release with jinja2's own output and errors. Next: faster rendering (about 8x slower than CPython today), `FileSystemLoader` (with a read grant), the sandboxed environment, and async rendering.
- **polars, natively.** polars dataframes (expressions, group-by, joins, pivots, CSV and JSON, polars' own printed tables) build natively from the next release, with file access held by the `read` and `write` grants. Next: date and time columns, Parquet, `polars.selectors`, and speed on large frames.
- **sqlite3 and duckdb, natively.** Programs using `sqlite3` (over the system's SQLite) and `duckdb` (over DuckDB's own engine) build natively from the next release, with DuckDB's own printed tables and database files held by the `read` and `write` grants. Next: Python functions in SQL, DuckDB results as data frames, and faster small queries.
- **safetensors and onnxruntime, natively.** Programs that load weights with `safetensors` or run a model with `onnxruntime` (ONNX Runtime's own engine, through its C API) build natively from the next release, with model and weights files held by the `read` and `write` grants. float16 and the small integer types load natively from the next release (math on them needs `astype`). Next: bfloat16 and 8-bit float dtypes, string tensors, `OrtValue` and `IOBinding`, and GPU providers.
- **Brevi files use the same native libraries.** From the next release a `.bv` file that imports numpy, jinja2, polars, sqlite3, the LLM SDKs or Brevi's other library copies runs them natively, a `.bv` file written in plain Python builds like a `.py` file, and Brevi `type` blocks take `fn` methods and `super()`. Next: Brevi-only files on the dynamic build.
- **Showcases.** The [showcases](/docs/showcases) page times real Python programs built with Brevi against CPython: an MCP server over SQLite (21x faster to its first answer), the official MCP time server built unchanged (22x), a token counter (14x) and Karpathy's micrograd (5.5x). Next: Karpathy's microgpt once the dynamic build is faster, and ports that need `fastmcp` and `click`.
- **Weekly releases.** One release a week, on Mondays, after that week's release test passes. Changes land on `main` under "Unreleased" in the [changelog](/docs/changelog) until then.
- **Cheaper heavy tasks.** Tell agents their Python is compiled so they write the plain solution, and make plain idioms (generators, string indexing) build typed and fast.

## Next

- **Homebrew.** `brew install ets-public/brevi/brevi`; the formula is ready. (`pip install brevi`, `npx brevi` and the MCP registry are live, and `cargo install brevi` follows with the next release.)
- **brevi.run.** The compiler as a hosted API for agents: check, run and test over HTTPS, sandboxed, with cached builds. Then a playground in the browser.
- **More of Python natively.** `match` statements and more standard modules in dynamic builds. (`async` / `await`, `asyncio`, async generators, `ExceptionGroup` and `except*` build natively from the next release.) Next for async: async programs that also use a library run in CPython, asyncio sockets, subprocesses and executors (which native HTTP servers need), and an event loop as fast as CPython's.

## Later

- **numpy-style arrays in `.bv`.** Brevi's own language gets an array type with what native numpy has for Python files, on the same engine.
- **Windows parity.** Library calls and `--standalone` on Windows; `--standalone` on macOS.
- **Faster cold builds**, for agents that build many one-off programs.
- **Larger and fresher benchmarks** on new model versions and other model families, with results published here (the release test already runs weekly and lands in the [weekly table](/docs/benchmarks#weekly-agent-code-benchmark)).

## Always

- Every program that once passed must keep passing: the full set of saved solutions is rerun on every change and on every new Rust and Python release.
- Brevi matches CPython or refuses. A silent difference is treated as the worst kind of bug.

Changes ship in releases listed in the [changelog](/docs/changelog).
