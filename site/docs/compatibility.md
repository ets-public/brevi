# What works, and limits
<!-- description: Which Python Brevi builds natively, how libraries work, typed versus dynamic builds, big integers, and the known gaps. -->

Brevi's aim for a Python file is simple: **the native program prints what CPython prints, or Brevi refuses to build it.** It does not meet that aim everywhere yet: on CPython's own tests some built programs still answer differently or crash, and the table below gives the count. This page says how much Python works today and where the edges are. For a program that matters, `brevi verify x.py --input tests/` runs the native build and CPython on the same inputs and certifies them only if they agree.

What "the same" covers: stdout byte for byte and the exit status. Text on stderr is not part of it, and neither is output that CPython itself changes from run to run (the order of a set of strings, `id()`, when `__del__` runs).

"Match" means stdout byte for byte and the same exit status. See [Benchmarks](/docs/benchmarks) for the method.

## Typed and dynamic builds

Brevi has two native ways to build a Python file, and picks between them on its own.

**Typed build**, the fast path. Brevi infers a fixed type for every value across the whole program and writes plain Rust. Most agent-written programs build this way. Python behaviour that shows in output is reproduced: unlimited integers, shared mutable objects (`r = rows[k]; r[0] -= 1` changes `rows`), dict printing and order, Python's float formatting and `round`, exception messages.

**Dynamic build**, the exact path. When a value changes type, a list mixes types, or the typed build would print something different from CPython (iterating a set, for example, where CPython's hash order shows), the whole program is built over a dynamic value type with CPython's own semantics: hashing and set order, formatting, exceptions, classes and method lookup. Still native, with no CPython involved, but slower than typed: typically somewhat faster than CPython rather than many times faster.

You do not choose; Brevi tries typed first. A file that does not build typed prints one [`{"path":...}` line](/docs/usage#which-path-ran) naming the function that kept it off the fast path; `brevi check --explain x.py` lists every reason.

## Python features

Works in native builds:

- Functions, default and keyword arguments, `*args` and `**kwargs`, closures, `nonlocal` and `global`, lambdas, decorators
- Classes, inheritance and `super()`, operator methods (`__add__`, `__eq__`, `__lt__`, `__repr__`, ...), properties
- Comprehensions, generators and `yield`, iterators, `zip`, `enumerate`, `map`, `filter`, `sorted` with `key`
- `try` / `except` / `else` / `finally`, `raise`, custom exceptions, `with` blocks; `except*` with `ExceptionGroup` in dynamic builds (from v0.26.0); `sys.exception()`, `sys.exc_info()` and `__context__` on an exception raised inside an `except` block in dynamic builds (from v0.26.0)
- `async def`, `await`, `async with` and `async for` (from v0.26.0), run by Brevi's own `asyncio`: see the table below
- f-strings with format specs, `%` formatting, `str.format`
- The walrus operator, slicing, tuple unpacking, chained comparisons
- Multi-file programs: sibling modules and packages imported as usual
- Reading stdin, arguments, files (`open`, `pathlib` reads and writes)

## numpy

From v0.26.0, a Python file that uses numpy's core builds with Brevi's own numpy, written in Rust: no CPython and no numpy at run time, and the same output as numpy 2.x byte for byte, printing included, on the machines described below (some last digits depend on the CPU and on numpy's thread count). A program that uses anything outside it is not built this way: it gets CPython's numpy as before (see [Libraries](#libraries-numpy-pandas)), so an answer is never half Brevi's and half numpy's.

What it has:

- Arrays of `float64`, `int64`, `float32`, `int32` and `bool`, with numpy's type rules (NEP 50: `np.array([1, 2]) + 1.5` is float64, a Python number never widens an array, `float32 + 0.1` stays float32), and numpy's scalars (`np.float64(2.5)` and `np.float32(0.1)` print as numpy 2 prints them). float32 math rounds once per operation as numpy's float32 loops do, and int32 wraps with numpy's overflow warnings. String arrays (`<U` with numpy's widths, truncation on assignment, comparisons, sorting, `+`, `where`, `unique`, `concatenate`, masks) and `np.str_` scalars, which act as Python strings; numpy's `np.char`/`np.strings` functions go to CPython's numpy for now. For float32 and int32, `@`/`dot`, `np.linalg`, ufunc `reduce`/`accumulate` and float32 `exp`/`log`/trig/powers other than squares and square roots go to CPython's numpy for now.
- Creation (`array`, `zeros`, `ones`, `full`, `arange`, `linspace`, `eye`, `*_like`, ...), shape changes (`reshape`, `.T`, `transpose`, `ravel`, `squeeze`, `expand_dims`, `stack`, `concatenate`, `vstack`, `hstack`, `tile`, `repeat`, `flip`, `roll`, `meshgrid`).
- Indexing as numpy does it: slices are views that share memory, boolean masks, integer-array indexing, `None`/`np.newaxis`, `...`, and assignment through any of them.
- Broadcasting, all the arithmetic and comparison operators (in place too), `@`, `dot`, `outer`, `cross`, `convolve`, and about 60 ufuncs (`sqrt`, `exp`, `log`, trig, `floor`, `round`, `maximum`, `isclose`, `where`, ...).
- Reductions with `axis` and `keepdims`: `sum`, `mean`, `std`, `var` (`ddof`), `prod`, `max`, `min`, `argmax`, `argmin`, `any`, `all`, `cumsum`, `cumprod`, `median`, `percentile`, `quantile`, `average`, the `nan*` forms. Sums add in numpy's own pairwise order, so float totals match to the last digit.
- `sort`, `argsort`, `unique` (with `return_counts` and friends), `searchsorted`, `nonzero`, `argwhere`, `diff`, `tolist`, `astype`, `set_printoptions`.
- numpy's errors (`ValueError: operands could not be broadcast together ...`, `AxisError`) and its warnings on stderr (`RuntimeWarning: divide by zero encountered in divide`).
- `np.random`, drawing the same numbers as numpy for the same seed: `default_rng(seed)` (numpy's SeedSequence and PCG64) with `random`, `integers` (`endpoint=`), `normal`, `standard_normal`, `uniform`, `exponential`, `choice` (`replace=False`, `p=`), `shuffle` and `permutation`; and the older `np.random.seed(n)` with `rand`, `randn`, `randint`, `random`, `uniform`, `normal`, `choice`, `shuffle`, `permutation`, `exponential` and `RandomState(n)`. Both APIs also have numpy's other distributions, with the same numbers and the same error messages: `poisson`, `binomial`, `geometric`, `negative_binomial`, `hypergeometric`, `zipf`, `logseries`, `gamma`, `standard_gamma`, `beta`, `chisquare`, `noncentral_chisquare`, `f`, `noncentral_f`, `standard_t`, `standard_cauchy`, `lognormal`, `laplace`, `logistic`, `gumbel`, `weibull`, `pareto`, `power`, `rayleigh`, `wald`, `vonmises`, `triangular`, `multinomial` and `dirichlet`. Array parameters broadcast as in numpy.

- `np.linalg.det`, `slogdet`, `solve` and `inv`, matching numpy to the last digit: Brevi runs OpenBLAS's own LU step by step, with the kernels OpenBLAS picks for AVX2 and AVX-512 CPUs.
- `np.linalg.lstsq`, `np.polyfit` (`full`, `w`, `rcond`, `cov`) and `np.polyval`, matching numpy to the last digit: Brevi runs LAPACK's dgelsd as numpy's OpenBLAS does. Up to 25 columns (or rows, for a wide matrix), so `polyfit` to degree 24; larger ones and inputs with `nan` or `inf` stop with a NotImplementedError for now.
- `np.linalg.norm` (vector and matrix orders, `axis`, `keepdims`) and `matrix_power`, `np.histogram` (`bins` as a count or edges, `range`, `density`), `np.cov`, `np.corrcoef`, `np.trapezoid`, and the ufunc methods `reduce` and `accumulate` of `np.add`, `np.multiply`, `np.maximum`, `np.minimum`, `np.logical_and` and `np.logical_or` (`np.maximum.accumulate(a)`).

Not yet (these go to CPython's numpy for now): `np.linalg.eig` and `svd`, `multivariate_normal`, `multivariate_hypergeometric` and `permuted`, other dtypes (bytes, complex, dates, `float16`, `int8`/`int16`, unsigned), and record arrays. (Tensors of `float16`, the small integer types and `complex64` loaded with safetensors or returned by onnxruntime stay native from v0.26.0: printing, indexing, reshaping and `astype` work, and math on them raises `NotImplementedError` naming the `astype` to use; see [safetensors and onnxruntime](#safetensors-and-onnxruntime).)

Two differences numpy itself has between machines: `exp`, `log`, `tanh`, `power` and `arctan` can differ from numpy in the last digit (numpy picks SIMD code for the CPU), and so can float `@` on CPUs other than AVX2 and AVX-512 ones (numpy calls OpenBLAS, which also differs by CPU). Float `np.dot` and `@` of two vectors, matrix @ vector, vector @ matrix and matrix @ matrix (`A @ A.T` too) (transposed and sliced operands too, and the large ones OpenBLAS splits across threads), `np.linalg.norm`, `det`, `solve`, `inv` and `lstsq` (and so `polyfit`) follow OpenBLAS's own order on AVX2 and AVX-512 CPUs, so they match numpy to the last digit on the same kind of machine. For `solve` and `inv` from 100 x 100 up, and `det` from about 140 x 140, numpy splits the work across threads and its last digit then depends on the thread count; Brevi gives what numpy gives on one thread (`OPENBLAS_NUM_THREADS=1`). numpy's default sort (quicksort) leaves equal values in an order of its own, which Brevi does not model: `np.argsort` of repeated values, and sorting or `np.unique` of `0.0` together with `-0.0`, stop with a NotImplementedError unless `kind="stable"` is given. `BREVI_NUMPY=0` turns Brevi's numpy off.

Speed: a loop over small arrays ran 3.7x faster than CPython with numpy, a grid simulation 2x, small statistics 40x (numpy's import time), and whole-array work on 2 million values about the same.

## tiktoken

From v0.26.0, a Python file that uses `tiktoken` builds with Brevi's own tiktoken: no CPython, no network and no file reads at run time, and the same tokens and errors as tiktoken 0.14.

- Every OpenAI encoding: `gpt2`, `r50k_base`, `p50k_base`, `p50k_edit`, `cl100k_base`, `o200k_base` and `o200k_harmony`, by `get_encoding` or by model name (`encoding_for_model("gpt-4o-mini")`, with tiktoken's model tables).
- `encode` (with `allowed_special` and `disallowed_special`), `encode_ordinary`, `encode_batch`, `encode_ordinary_batch`, `decode` (`errors=`), `decode_bytes`, `decode_batch`, `decode_bytes_batch`, `decode_tokens_bytes`, `decode_with_offsets`, `encode_single_token`, `decode_single_token_bytes`, `token_byte_values`, `is_special_token`, `n_vocab`, `max_token_value`, `eot_token`, `special_tokens_set`, `_special_tokens`, `_pat_str` and `_mergeable_ranks`.
- `tiktoken.Encoding(...)` with your own vocabulary, or an encoding extended with chat tokens as tiktoken's README shows (`pat_str=cl100k_base._pat_str`, `special_tokens={**cl100k_base._special_tokens, "<|im_start|>": 100264}`).

The compiler builds the vocabularies a program names into the binary: from tiktoken's cache (`TIKTOKEN_CACHE_DIR`, `DATA_GYM_CACHE_DIR` or the temp directory, as tiktoken looks), else downloaded once from OpenAI's servers with `curl`, checked against tiktoken's hashes and saved in that cache. A name the build cannot see (`get_encoding(name)`) builds all four vocabularies in, about 3 MB. A built program tokenizes under `--sandbox` with nothing granted.

Text is split by a regex engine written for tiktoken's patterns (leftmost-first alternation, possessive and lazy repeats, atomic groups, lookahead, `\p{L}`-style classes read off tiktoken's own regex library, so the Unicode version is the same), then merged by BPE in tiktoken's order. Not native yet (the program runs with CPython's tiktoken, or `--native` refuses it): `encode_to_numpy`, `encode_with_unstable`, `tiktoken.load`, `tiktoken.core` and the other submodules, plugins, and `Encoding(pat_str=...)` with a pattern the engine lacks (lookbehind, backreferences) or one it cannot see at build time.

## tokenizers

From v0.26.0, a Python file that uses Hugging Face `tokenizers` builds with Brevi's own port of tokenizers 0.23.3: no CPython at run time, and the same ids, tokens, offsets, word ids, masks, decoded text and errors.

- Load a tokenizer with `Tokenizer.from_pretrained("bert-base-uncased")` (a literal model id, and a literal `revision` if you give one), `Tokenizer.from_file("tokenizer.json")` (a literal path) or `Tokenizer.from_str(json_text)`.
- Models: BPE (byte-level as in GPT-2, RoBERTa, Qwen and Llama 3; SentencePiece-style with byte fallback as in Llama 2 and TinyLlama), WordPiece (BERT, MiniLM, other sentence-transformers) and WordLevel, with the normalizers, pre-tokenizers, post-processors and decoders those tokenizers use.

Not native yet (the program runs with CPython's library, or `--sandbox` refuses it unless the caller grants `--allow-py sqlite3` or `--allow-py duckdb`): in sqlite3, `create_function`, `create_aggregate`, `create_window_function`, `create_collation`, `set_authorizer`, `set_progress_handler`, `set_trace_callback`, extensions, `backup`, `blobopen` and `Blob`, `serialize` and `deserialize`, `getconfig` and `setconfig`, `*FromTicks`, `check_same_thread=False`, and `bytearray` or `memoryview` values; in duckdb, pandas, numpy, Arrow and polars results and sources (`df`, `fetchnumpy`, `arrow`, `pl`, `from_df`, `register`, ...), `create_function`, `install_extension` and `load_extension`, filesystems, the expression API (`duckdb.col`, `ColumnExpression`, ...), `duckdb.typing` and the type constructors, the file readers and writers of the API (`duckdb.read_csv`, `to_csv`, `to_parquet`, ...; SQL's `read_csv` works), `sql_query`, `explain`, `describe`, `materialize`, `with_columns`, `value_counts`, `pivot`, `unpivot`, the window shortcuts (`rank`, `lag`, ...), `Appender`, `tokenize` and `extract_statements`. Raised at run time instead: duckdb values of type UUID, `TIMESTAMP WITH TIME ZONE`, `TIME WITH TIME ZONE`, BIT, UNION and BIGNUM, infinite dates and timestamps, and a relation step over a statement that is not a query (`con.sql("insert ...").filter(...)`). Differences: sqlite3 uses the system's SQLite (3.45 here, where CPython's own build may carry another version, so `sqlite_version` and newer SQL functions can differ), returns `bytes` for blobs where CPython can be asked for a `memoryview`, writes no `DeprecationWarning`, and ignores `check_same_thread`; duckdb's table printer does not pretty-print JSON and nested values when it wraps the rows of a narrow table, a relation's unnamed alias is a different random name, an error inside a derived step can show a different `LINE` of context, and a read-only database refusing a parameterized statement names it `EXECUTE`. A program built with duckdb needs the duckdb package (or `libduckdb`) where it runs, at the path found when it was built; on Windows this is the wheel's own C API, so a Windows build needs duckdb 1.5 or later.

## safetensors and onnxruntime

From v0.26.0, a Python file that loads model weights with `safetensors` or runs a model with `onnxruntime` builds natively, on Brevi's own numpy: no CPython at run time, and the same arrays, printed output and error messages as the safetensors 0.8 package (numpy framework) and onnxruntime 1.29 to 1.31.

- **safetensors** is a port of the format's Rust crate: headers are read and checked as the crate does (with serde_json's error messages and positions), tensors are written in the crate's order with its padding, and slices follow its indexing rules. Covered: `safe_open` (`framework="np"` or `"numpy"`, `keys`, `offset_keys`, `metadata`, `get_tensor`, `get_tensors`, `get_slice` with ints, slices with steps and one `...`, `get_shape`, `get_dtype`, use as a context manager), `safetensors.numpy` (`save`, `save_file`, `load`, `load_file`, with `metadata`), `SafetensorError`, and tensors of dtype F64, F32, I64, I32 and BOOL.
- **onnxruntime** runs ONNX Runtime itself through its C API: the library inside the installed onnxruntime package (found when the program is built), `libonnxruntime`, or `BREVI_ORT_LIB` outside the sandbox. On Windows (from v0.27.0) it loads `capi/onnxruntime.dll` from the wheel, so onnxruntime 1.16 or later is needed (1.13's wheel has no C API DLL), and model/optimized-model/profiling paths are passed as UTF-16. Covered: `InferenceSession` from a path or model bytes (with `sess_options` and `providers`), `get_inputs`, `get_outputs`, `get_overridable_initializers` (`NodeArg` with `name`, `type`, `shape`), `get_modelmeta`, `get_providers`, `get_provider_options`, `set_providers`, `run` (output names, numpy or list inputs, `RunOptions`), `SessionOptions` (optimization level, execution mode, thread counts, memory pattern and arena, logging, deterministic compute, `add_session_config_entry`), `RunOptions`, the enums, `get_available_providers`, `get_device`, `get_version_string`, `get_build_info`, and the binding's exception classes and `[ONNXRuntimeError]` messages. Results come back as numpy arrays (float32, float64, int64, int32, bool), and sequences of maps (ZipMap) as lists of dicts, as in CPython.

Under `--sandbox`, reading a weights or model file needs `--allow read`, and `save_file`, an optimized model (`optimized_model_filepath`), profiling, or a session config entry that names a file need `--allow write` (config entries naming files need both). A model given as bytes needs nothing, unless its weights are in external data files: then it needs `--allow read`, and the session is refused before ONNX Runtime opens anything. Brevi's numpy itself needs no grant.

Speed: a small safetensors script runs in about 5 ms where CPython takes about 100 ms, and a small ONNX script in about 70 ms where CPython takes about 245 ms (most of it importing numpy and onnxruntime); inference runs on the same engine, so large models take the same time (a 20-run CNN and MLP: 0.11 s against CPython's 0.24 s). Weaker: loading a large weights file is about 1.3x slower than CPython (Brevi reads and copies the bytes, where the package maps the file), and work done on the results afterwards is as fast as Brevi's numpy is.

Not native yet (the program runs with CPython's library, or `--sandbox` refuses it unless the caller grants `--allow-py safetensors` or `--allow-py onnxruntime`): in safetensors, the torch, tensorflow, flax, mlx and paddle frameworks, devices other than the CPU, `serialize`, `serialize_file`, `deserialize` and `TensorSpec`, and `bytearray` or `memoryview` inputs; in onnxruntime, `OrtValue`, `IOBinding`, `run_with_ort_values`, `run_async`, sparse tensors, custom op libraries, LoRA adapters, model compilation, `add_initializer` and `add_external_initializers`, free dimension overrides, execution providers other than the CPU, `end_profiling`, tuning results, `set_seed`, and the `training`, `quantization`, `transformers` and `tools` packages. Raised at run time instead (`NotImplementedError`): safetensors tensors of dtypes Brevi's numpy lacks (F16, BF16, F8, U8, I8, I16, U16, U32, U64, C64), saving an array with negative strides, ONNX string tensor outputs (numpy object arrays), and outputs of float16, uint8 and the other types Brevi's numpy lacks, and optional or sparse values. Programs whose numpy part goes beyond Brevi's numpy (for example float32 `@` or other float32-only functions) run with CPython's libraries. Differences: Brevi's `load` and `save` keep tensor and metadata order fixed (offset order and sorted), where the package's order varies from run to run; an I/O error in `save_file` names the target file, not the package's temporary file; ONNX `int64` results print with `dtype=int64` as CPython's do, but arrays computed from them do not; and onnxruntime's `NotImplemented` exception class is not there (its name is Python's constant). A program built with onnxruntime needs the onnxruntime package (or `libonnxruntime`) where it runs, at the path found when it was built; on Windows that is `capi/onnxruntime.dll` from onnxruntime 1.16 or later.

## mcp (MCP servers)

From v0.26.0, a Python MCP server written with the official `mcp` SDK builds into one native binary, with Brevi's own copy of the SDK written to answer as mcp 2.3.0 does: no CPython, no virtualenv, nothing to install next to it. The binary speaks stdio, as every MCP client starts a local server, and answers both protocol eras the SDK serves: the handshake versions 2024-11-05 to 2025-11-25 (`initialize`) and 2026-07-28 (`server/discover` and per-request `_meta`). It starts and answers the first request in about 25 ms, where CPython takes about 0.75 s to import the SDK.

- **`MCPServer`** (the FastMCP-style API): `@mcp.tool()`, `@mcp.resource()` (fixed URIs and templates, with `{name}`, `{path*}` and query variables, and the SDK's path checks), `@mcp.prompt()`, `@mcp.completion()`, `add_tool` / `remove_tool` / `add_resource` / `add_prompt`, `instructions`, `version`, `website_url`, `icons`, `lifespan`, and `run()` on stdio. Tool input schemas, `outputSchema` and `structuredContent` come from the type hints as the SDK makes them (pydantic models, `Annotated[..., Field(...)]`, `Literal`, `Optional`, lists and dicts), arguments are validated and coerced as pydantic does, and errors become the SDK's `isError` results and JSON-RPC errors, word for word. `Context`: `info` / `debug` / `warning` / `error` / `log`, `report_progress`, `read_resource`, `request_id`, `session`, the lifespan state. `Image` and `Audio` from bytes, `TextContent` and the other content types, `UserMessage` / `AssistantMessage`, `ToolError`, `ResourceError`, `MCPError`. From v0.26.0, server middleware: `server.middleware.append(fn)` and `MCPServer(middleware=[...])`, with `ServerRequestContext`, `CallNext` and `HandlerResult` from `mcp.server.context`; each message passes through the chain outermost first, as in the SDK.
- **The low-level `Server`** (`mcp.server.lowlevel`) with its `on_*` handlers, `NotificationOptions`, `create_initialization_options`, and `mcp.server.stdio.stdio_server()`; `mcp.types` is the SDK's own models, generated from the SDK (`tools/gen_mcp_types.py`).

On Windows (from v0.27.0) the same native server runs both transports: stdio claims the process's stdin/stdout with `DuplicateHandle` and checks the pipe for bytes with `PeekNamedPipe`, and streamable-HTTP/SSE keeps its listening socket and connections in `TcpStream` tables waited on with `WSAPoll` (`BCryptGenRandom` for session ids). No DLL or Python install is needed at run time.
- **The wire behaviour** follows the SDK's dispatcher: requests run concurrently, `notifications/cancelled` cancels one (it is never answered), requests still running when the client hangs up get "Connection closed", params and results are checked against the negotiated version's schema, and bad JSON lines are dropped.

`brevi verify server.py --input session.jsonl` certifies a server: a `.jsonl` input to a file that imports `mcp` is played as a client session, each request sent once the reply to the one before it is in (see [Verify against CPython](/docs/usage#verify-against-cpython)). The tests replay eight such sessions against four servers (`tests/mcp_sdk/`) and match CPython's transcripts byte for byte.

- **Over HTTP**, from v0.26.0: `mcp.run(transport="streamable-http")` and `mcp.run(transport="sse")` (and `run_streamable_http_async` / `run_sse_async`) serve natively on Brevi's own HTTP/1.1 server, with the SDK's arguments (`host`, `port`, `streamable_http_path`, `json_response`, `stateless_http`, `session_idle_timeout`, `max_sessions`, `max_request_body_size`, `transport_security`, `sse_path`, `message_path`). Sessions, SSE and JSON responses, the standalone GET stream, `DELETE`, the 2026-07-28 single-request exchange with its routing headers, and the Host and Origin checks a local server turns on all answer as the SDK on uvicorn does: the tests compare four transcripts with CPython's request for request (`tests/mcp_sdk/http/`) and run the official client over both transports.

Under `--sandbox` a stdio server needs no grant at all: it only reads stdin and writes stdout. An HTTP server needs the network grant for the host it listens on (`--allow-net 127.0.0.1`, or `--allow net`).

Change events are native: `ctx.notify_tools_changed()`, `notify_prompts_changed()`, `notify_resources_changed()` and `notify_resource_updated(uri)` publish to `subscriptions/listen` streams (2026-07-28 clients, over stdio and streamable HTTP), each filtered by what the client asked for and stamped with its subscription id; `MCPServer(subscriptions=bus)` takes your own bus, and `mcp.server.subscriptions` has `InMemorySubscriptionBus` and `ListenHandler` for the low-level `Server`. Handshake-era clients get `resources/subscribe` / `resources/unsubscribe` handlers and `ctx.session.send_resource_updated(uri)` (over streamable HTTP these go on the GET stream). (From v0.27.0.)

Differences from CPython: sync tools run on the event loop, not in a worker thread (a slow sync tool holds up the others; make it `async`); `MCPDeprecationWarning`s are not printed; logged tracebacks name the exceptions but not CPython's frames. Not native yet (the program runs with CPython's SDK, or `--native` refuses it): the Starlette apps (`streamable_http_app()`, `sse_app()`, `custom_route`), resumability (`event_store`), auth, requests from the server to the client (sampling with `create_message`, elicitation, `list_roots`), `Image(path=...)` / `Audio(path=...)` (they read files), extensions, and the client side (`ClientSession`, `stdio_client`).

## Libraries (numpy, pandas, ...)

A Python file that imports a module Brevi does not build itself (pandas, yaml, Pillow, ...) still builds natively: each library call runs in CPython, loaded into the native program, so results are CPython's own, and the rest of the program stays native and fast. Brevi's own modules (math, re, json, datetime, ...) stay native: what the typed build lacks of them goes to the dynamic build, never to CPython (from v0.24.3; see [What runs native](#what-runs-native)).

Limits today:

- Under `--sandbox` (and in the MCP tools, which sandbox by default) a program that imports such a library is refused unless the caller grants it with `--allow-py pydantic` (MCP: `allow_py`) or `--allow native`; an `# allow native` line in the file grants nothing there (from v0.24.6; from v0.24.1 to v0.24.5 the line was enough). Path functions of `os` and `pathlib` and the common `random` functions work without it (from v0.24.2; see [Sandbox](/docs/usage#sandbox)).
- The built program needs `python3` with its shared library (`libpython`) on the machine where it runs, unless built with `--standalone`, which carries CPython and the imported packages in the binary (Linux only).
- A library program the typed build rejects goes to the dynamic build, which calls the library through CPython the same way and keeps the rest native (from v0.24.6). Classes built on a library's classes (`class Post(BaseModel)`) run in CPython as a whole. Such a class falls back to CPython for the whole file if it sits inside a function, uses a name of the program that is not an import, or is subclassed in another file. The path line lists what CPython runs (`"py":[...]`).
- `async` code next to such a library keeps the dynamic build and Brevi's own event loop (from v0.26.0), unless a coroutine could cross between the two: a coroutine function or lambda handed to the library, an async method on a subclass of one of its classes, an `async def` it decorates, or something it made being awaited or handed to asyncio (an async library such as `aiohttp`). Those programs run in CPython.
- On Windows (from v0.27.0), library calls run in CPython through the bridge too (the `python` on PATH must have its DLL), and generators and `async` build there too (Win32 fibers); Brevi's own sqlite3, duckdb, onnxruntime, requests/httpx and mcp (stdio and HTTP/SSE) also run natively there (each needs its engine's Windows library: Windows' own `winsqlite3.dll`, the duckdb wheel's C API, `capi/onnxruntime.dll` from onnxruntime 1.16+, and Python's OpenSSL DLLs; mcp needs none). `--standalone` is Linux only.
- In typed builds, a `with` block on a library object does not pass exception details to its `__exit__`, and named functions cannot yet be passed as callbacks to a library (lambdas can). Dynamic builds do both.

## Integers

Python integers have no size limit, and neither do Brevi's. In typed builds a value starts as a 64-bit integer and becomes a big integer as soon as it could pass 64 bits, through returns, closures, `nonlocal` and `global` and the `//` and `%` operators. Integers never silently wrap around, as they would in a release-mode Rust program. Powers of literals are worked out at compile time, so `3 ** 50 % 1000000007` gives Python's answer. Dynamic builds use big integers with CPython's semantics throughout, including bit operations on numbers of any size.

## Errors and run-time behaviour

A Python file keeps Python's run-time behaviour: a mistake Python only finds when a line runs (an index out of range, a bad `int()` argument) raises at that point, with the same exception type. The exception is a sure mistake, a name that is never defined, a method no Python type has, or text added to a number: `brevi check` and `brevi build` report that before the program runs, with a fix, and `brevi run` names it in its fallback note. Code that may never run (under `sys.version_info`, `TYPE_CHECKING` or `if False`, or in an `except` block) is left alone. Run-time error messages are shorter than CPython's tracebacks; error text on stderr is not part of the "same output" promise, but stdout and the exit status are.

## Known gaps

These are tracked on the [roadmap](/docs/roadmap):

- **Classes built on a library's classes** (`class Post(BaseModel)`) run in CPython as a whole, and in some layouts send the whole file to CPython.
- **Dynamic builds are slower** than typed ones; widening what the typed build accepts is ongoing work.
- **`match` and `eval` of run-time text** are not built natively (async generators are, from v0.26.0).
- **Built programs that differ from CPython.** On CPython's own tests 44 built programs still answer differently and 5 crash (see [In numbers](#in-numbers)). Some library paths also raise `NotImplementedError` at run time instead of refusing at build time: numpy `argsort` on repeated values, some safetensors dtypes, duckdb UUID and timezone values.
- **`brevi run` falls back to `python3` quietly.** A file Brevi cannot build runs with CPython, with one line on stderr; that run gets no speed-up and no native checks. Use `--native` (or `brevi build`) to get an error instead.
- **Cold builds** take about 0.25 seconds for a tiny program (about 1.5 s with `--release`), and a median of about 1.2 s for a typical saved agent program with no cache; the very first build after installing also builds Brevi's runtime once, about 5 to 15 seconds. That still matters for agents that build many one-off programs; repeat builds are cached.
