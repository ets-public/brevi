Experimental · archived

Brevi was an experiment, and it is archived.

Brevi tried to compile Python MCP servers and command-line tools into one native binary that needs no Python and starts fast. It works on small programs, such as the showcases below, but it failed its first test on real servers: of the ten most-downloaded Python MCP servers on PyPI, built unchanged on 19 November 2026 with Brevi 0.28.3, none built natively. All ten needed the CPython bridge, and so Python on the run machine, and started at 1.00x to 1.16x CPython's time to the first tool call.

Read the real-server report Read the post-mortem

We are not developing Brevi further and do not recommend it for new projects. The rest of this page describes what Brevi does on the programs it does build, with the limits that apply.

From server.py to one file

Already have a Python MCP server? Ship it as one binary without rewriting it in Go or Rust. The full guide.

  1. Keep your Python

    An MCP server on the official mcp SDK, or a CLI on argparse, in one file or a package. Brevi builds the standard library and common packages (mcp, pydantic, httpx, requests, sqlite3, tiktoken) from its own native copies.

  2. Build it once

    brevi build server.py --release -o my-server compiles it through Rust. If an import has to run in CPython instead, the build prints one line naming it, so you know before you ship.

  3. Ship the file

    Copy it to the machine that runs it, register it with claude mcp add my-server -- ./my-server or any MCP client, or put a CLI on the PATH. No install step for your users.

What changes for the people who run it

An MCP client starts a server for each session, and a CLI starts on every call, so start-up is time the user waits. CPython spends most of it importing packages; a Brevi binary skips that.

What to know before you ship

The limits today, stated plainly. The roadmap says which ones are being worked on.

{"path":"pybridge",...}

Most real servers need CPython today

A package Brevi does not build itself runs in CPython inside the binary. That binary needs Python 3.13 and the packages it was built against (the build venv's site-packages) on the run machine, and starts no faster than CPython. Of the ten most-downloaded Python MCP servers on PyPI, built unchanged on 19 November with Brevi 0.28.3, none built natively: all ten took the bridge, at 1.00x to 1.16x CPython's time to the first tool call (report). --standalone (Linux and Windows) carries CPython instead, but misses packages imported lazily and broke 4 of the 10.

Linux · macOS · Windows

Where the binaries run

Linux binaries link the system glibc, so build on the oldest Linux you target; there is no static build yet. Brevi is released for macOS, but programs built on macOS are not yet tested in CI. Windows is a beta, with its limits in Known issues.

0.85x median

Start-up is the win, not throughput

Most servers build over dynamic values, which run at about CPython's speed (0.5x to 1.4x on our compute benchmarks). A server that spends its time waiting on I/O or a model will not run its tool calls faster.

RSS over days

Long-running servers

A built program does not yet free some memory, such as reference cycles. That is fine for a session-length server; watch the memory of one that runs for days. Making it stay flat is on the roadmap.

mcp · pydantic · asyncio

Not every server builds natively

Brevi's copy of the MCP SDK follows the current SDK's MCPServer on stdio. A server that uses sampling, elicitation, auth, or the SSE and streamable HTTP apps runs on CPython's mcp instead, and servers written for the older FastMCP import do not build natively yet. We are building popular servers and CLIs unchanged and will publish the raw results, failures included.

--sandbox

Security, plainly

A built binary has the same access as any program you run. Brevi's --sandbox, for running code an agent wrote, is a policy layer, not an isolation boundary: there is no container or VM around the program, and --allow-py and --allow native are full trust. Run untrusted code in a container or VM. No external security audit yet: we have not had an external audit; we are seeking funding for one. Until then, do not run hostile code under the sandbox.
